Comparison · different, not better

How Fomoxa differs

Every format here is good at what it was designed for. This page lists what each one guarantees, so you can tell which guarantees your problem needs.

Binary IDLs

Fomoxa, Protobuf, FlatBuffers, Cap'n Proto

All four use a schema known to both ends. They differ in what the schema lets the bytes vary on, and in how much of that variation is allowed.

Deterministic

Fomoxa, Borsh, BCS

The closest relatives. All three give a value exactly one encoding, write integers at a fixed width in little endian, and write struct fields in declaration order with no tags. They differ in the types they carry.

If your system already runs on Borsh or BCS, you have the determinism guarantee Fomoxa is built around. Fomoxa's differences are narrower: fewer types, float bits kept exactly, and a specification that belongs to no single language.

Schemaless

Fomoxa, JSON, MessagePack

JSON and MessagePack are self-describing: a reader needs no schema. Fomoxa is the opposite: without the schema the bytes mean nothing.

Same value

One Player, five encodings

Player{ id: 100, name: "Alice" }. Byte counts are for this value only. Change the value and the ranking can change. 

# Fomoxa · 13 bytes
64 00 00 00 05 00 00 00 41 6C 69 63 65
id           length       A  l  i  c  e
# the only valid encoding
# Protobuf · 9 bytes    (id = 1, name = 2)
08 64 12 05 41 6C 69 63 65
tag varint   tag len  A  l  i  c  e
# fields may also appear in another order
# MessagePack · 16 bytes  (as a map)
82 A2 69 64 64 A4 6E 61 6D 65 A5 41 6C 69 63 65
# 100 may also be written CC 64, D0 64, ...
# 8 bytes as an array: 92 64 A5 41 6C 69 63 65
# JSON · 25 bytes
{"id":100,"name":"Alice"}
# equally valid:
{"name":"Alice","id":1e2}

Fomoxa is not the smallest here: fixed-width integers cost bytes that varints save. What it buys is that the first block is the only valid answer, in every conforming implementation.

Where Fomoxa is ahead
  • Small messages with typical data: the fastest of the four to encode and decode.
  • Floats and random ids: 17–21% smaller than Protobuf, because there are no tags.
  • Against canonical Cap'n Proto on small messages: 8–15x faster to encode, about 4x faster to decode.
  • Against prost on typical data: 1.7–9.4x faster to encode, 1.4–2.8x faster to decode.
Where it is not
  • Arrays of fixed-size structs: Cap'n Proto encodes batch-1000 2.6x faster and decodes it 2x faster.
  • Canonical Cap'n Proto ties Fomoxa on batch-1000 encode and still decodes batches 1.6–1.8x faster.
  • Mostly-zero data: Protobuf skips zero fields, so a player standing still is 2 bytes against 21, and decodes faster.
  • Small integers: Protobuf's varints make stats 24 bytes against 38.

Read it with its limits: Rust only, one implementation per format, synthetic data, one laptop under WSL2, loopback only. Every decoder builds the same owned struct; reading Cap'n Proto in place, as it is designed to be read, is cheaper and not measured. In the example game, at 1000 players the full server stacks were indistinguishable (0.3 ms p50), because the codec is a tiny share of the tick. Run scripts/run.sh on your own message shapes before you decide.

Choosing

When something else fits better

Choose Fomoxa when
  • Two implementations, in different languages, must produce identical bytes.
  • You sign, hash or deduplicate payloads.
  • You run replay, lockstep or state checksums across machines.
  • Both ends ship from the same schema and can deploy together.
Choose another format when
  • Clients and servers evolve independently for years: Protobuf's field numbers fit better.
  • You need random access into large buffers without decoding: FlatBuffers or Cap'n Proto.
  • Readers do not know the schema, or humans read the data: JSON.
  • You need optional fields or explicit nulls on the wire.
  • You need deterministic bytes and fast reads of large arrays: Cap'n Proto's canonical form.
  • Your system already runs on Borsh or BCS: you have the same determinism guarantee.

The full reasoning is in RFC-0001 §3.3 and §5.3.
