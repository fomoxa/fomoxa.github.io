0x01Problem

Why another protocol?

Because “the same data” and “the same bytes” are not the same requirement — and every mainstream format solves only the first one.

Protobuf, MessagePack and JSON were designed to be flexible. Flexible means more than one valid encoding exists for a single value. For most systems that is a feature. For a system that hashes, signs, replays or diffs its payloads, it is the entire problem.

Protocol Buffers

The official documentation states serialization is not canonical: map ordering, unknown-field retention and version differences can each change the output bytes of a semantically identical message.

Same message → different bytes

MessagePack

One integer has several valid representations — int8, int16, int32. Two encoders that choose differently are both conformant, and produce different streams.

Multiple valid encodings

JSON

Key order is unspecified, float formatting differs between runtimes, whitespace is free. Textual equality and byte equality drift apart immediately.

No byte-level contract

What that costs

Hash / sign
A signature is computed over bytes. Re-encode the same object on another runtime and the signature stops verifying — although nothing about the data changed.
Replay / lockstep
Two machines fed the same input log must reach the same world state. One divergent bit desynchronises the simulation, silently and unreproducibly.
Cross-SDK tests
Byte comparison is the only honest proof that two SDKs are compatible. Without canonical output there is nothing to compare — the suite can only assert “it round-trips locally”.
Content addressing
Identical content must produce an identical digest, or caching and deduplication quietly stop working.

Cyclone’s answer is not a smarter algorithm. It is the removal of every choice: wherever an encoder can choose, two encoders eventually choose differently.

0x02Philosophy

Ten principles, one decision rule.

Every proposed change answers a single question: does it violate one of these? If yes, it is not part of Cyclone.

01 Specification First The spec is the single source of truth. It is never changed to accommodate an implementation.
02 Protocol over Framework Cyclone defines how data appears on the wire — not an API, not a runtime.
03 User Owns the Model No mandatory DTO layer, no base class. Cyclone reads the fields you mark, and ignores the rest.
04 Compile-time over Runtime Anything decidable at build time is decided at build time.
05 Zero Runtime Reflection No runtime type inspection, no runtime schema parsing. AOT and bare-metal targets stay viable.
06 Minimal Wire Format Send the data, never a description of the data. No field names, no type info, no tags, no padding.
07 Deterministic by Design One input, exactly one output byte sequence. No two valid encodings exist.
08 Language Neutral No language is the reference language. The spec defines behaviour, not idiom.
09 Implementation Independent Parser, macro, source generator, handwritten, FPGA — the spec cares only about the result.
10 Implementation Replaceable Swap the whole implementation; the wire format does not move. The reference impl is not the standard.

The test applied to every sentence of the specification: could somebody writing an encoder in assembly on an 8-bit microcontroller follow it? If not, that sentence describes an implementation, and it does not belong in the spec.

0x03Ecosystem

Open call for implementations

Cyclone is a protocol specification. We need your help to bring it to every language and platform.

The wire format is stable enough to build against. What the project needs now is not more specification — it is encoders, decoders and code generators, each proven against the same conformance vectors. Open an issue to claim a row.

0x04Byte map

Read the actual bytes

A full Player — nested struct, string, enum, bool, array of structs — encodes to 49 bytes. Hover a field to light up the bytes it owns, or hover a byte to find its owner.

Hex dump · 49 bytes Position is the only identifier
00000000 6400000005000000416C6963650000C0
00000010 3F000020400000604001000000010100
00000020 0000070000000500000053776F726401
00000030 00
Total49 bytes · 0 bytes of metadata

Nothing separates the fields. No length prefix on the struct, no delimiter between Position and State, no terminator at the end. The decoder knows which field it is reading purely from how far the cursor has advanced — which is exactly why reordering a field is a breaking change, and why renaming one is free.

Edge cases, settled in the normative text

Float · bit-pattern preservation

Floats serialize their IEEE 754 bit representation exactly. No normalization, no canonicalization. Two NaN payloads are two different values on the wire — an implementation that rewrites them has modified user data. 

0x7FC00001 → [01 00 C0 7F]   preserved
0x7FC00001 → [00 00 C0 7F]   canonicalized ✗

Bool · strictly 0x00 / 0x01

An encoder may emit only 0x00 or 0x01; a decoder rejects everything else. “Non-zero means true” is not permitted, however truthy the source language considers the value. 

[00] → false        [01] → true
[02] → reject        [FF] → reject

Enum · always UInt32

Every enum is four bytes, however few members it declares. A protocol decision, not a storage optimization — there is nothing for two peers to negotiate. An undefined value is a hard error, never a graceful skip. 

Walk (1)        → [01 00 00 00]
99 ∉ {0,1,2,3}  → reject

Length overflow · normative DoS guard

A length or count larger than the bytes actually remaining must be rejected before any allocation. That check is normative and configuration-independent; per-SDK limits only tighten it further. 

count = 4294967295, 0 bytes left
  → reject before allocating

effective = min(remaining, configured)

0x05Trade-offs

What Cyclone deliberately will not do

Determinism is bought with rigidity. Here is the invoice, in full, before you adopt anything.

✕

No schema evolution

There is no field ID, so there is no unknown-field skipping and nothing to reserve. Adding, removing or reordering a field changes the byte stream. Every schema edit is a breaking change, and the specification does not pretend otherwise.

✕

No backward / forward compatibility

Both peers upgrade together. If old clients must keep talking to a new server, Cyclone is the wrong tool and a tagged format is the right one. Versioning, where you need it, is negotiated above the protocol.

✕

No metadata, no self-description

The stream carries data and nothing else, so the receiver must already know the exact field order and types. The dangerous corollary: decoding against the wrong definition usually raises no error at all — it produces wrong values, quietly. Keeping both sides in step is your responsibility.

✕

No schema definition layer

There is no IDL, no .cyclone file, no separate schema document to compile. Your own annotated type is the definition — the single source of truth — and a frontend needs to extract only three things from it: the type, its fields, and each field’s Cyclone type. Everything else about your language stays your language’s business.

✕

No Optional, no nullable, no defaults

Every field carries a value. There is no absent-field encoding in v1 — which is precisely why there is no ambiguity about how absence would be written.

✕

No transport, no framing, no crypto

Delivery, ordering, retransmission, integrity, encryption and compression belong to the layers around Cyclone. The specification stops where the bytes are formed.

If your schema changes weekly and your clients update on their own schedule → use Protobuf.
If a byte-identical encoding is a correctness requirement → keep reading.
