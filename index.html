Fomoxa Protocol

A deterministic binary wire format.
Nothing more. Nothing less.

Fomoxa defines how logical data becomes bytes. And how bytes become logical data.

Definition

What is Fomoxa?

Fomoxa is a protocol.

Fomoxa is not

  • × RPC
  • × Networking
  • × Runtime
  • × Serialization Library

Fomoxa only specifies

  1. Model
  2. Bytes
  3. Model

Transport, retransmission, ordering, matchmaking, encryption, compression, checksums - build all of it on top of Fomoxa. The specification stops exactly where the bytes are formed.

Philosophy

Ten principles, two layers.

Seven are conformance conditions. Three are choices the Reference Implementation made. Mix the two and a protocol quietly turns into a framework.

Principles of the Specification

Violate one of these and it is not Fomoxa.

01 Specification First The spec is the single source of truth. Never change it to accommodate an implementation.
02 Protocol over Framework Fomoxa defines how data appears on the wire. Not an API, not a runtime.
03 Minimal Wire Format Send the data, never a description of the data. No field names, no type info, no tags, no padding.
04 Deterministic by Design One value, exactly one byte sequence. Two valid encodings of the same data must not exist.
05 Language Neutral No language is the reference language. Nothing in the format favours one type system.
06 Implementation Independent No mandated parser, macro, or generator. The spec describes bytes and stops.
07 Implementation Replaceable The Reference Implementation is not the standard. Replace it entirely and the wire format holds.

Principles of the Reference Implementation

Design choices, not conformance conditions. Another implementation may choose differently. The bytes must not move.

08 User Owns the Model No mandatory DTO layer, no base class. The RI reads the fields you mark and ignores the rest.
09 Compile-time over Runtime Anything decidable at build time is decided at build time.
10 Zero Runtime Reflection The wire format permits it. The spec does not require it. AOT and bare-metal targets stay viable.

The decision rule, in two questions. One: is this statement observable from the byte stream? If not, it belongs to the Reference Implementation and must not enter the spec. Two: does it violate one of the seven above? If yes, it is not part of Fomoxa.

Trade-offs

What Fomoxa deliberately does not do

Each of these is the direct cost of a guarantee above. None of them is on a roadmap.

✕

Schema evolution only at the end

Position is the only field identifier. Append or remove a field at the end of a Model and the wire holds (Version Skew, RFC-0002 §9.1). Inserting a field in the middle, reordering fields, changing a field's type: breaking change.

✕

Compatibility only at the trailing edge

An old client reads a new server's message under one condition. The only change is a field appended at the end. The extra bytes are discarded (Version Skew, RFC-0002 §9.1). A field inserted or changed in the middle is a hard break. Both ends deploy together, or not at all.

✕

No metadata, not self-describing

The stream carries no field names, types or tags. The receiver must already know the field order and types. The dangerous corollary: decoding against the wrong definition usually raises no error at all. It produces wrong values, quietly.

✕

No mandated IDL

The source of truth is the Schema. The spec does not dictate how you write the Schema down. No mandatory IDL, no mandatory .fomoxa file. The Reference Implementation expresses the Schema as annotations on your existing type. It extracts exactly three things: the type, its fields, and each field's Fomoxa type. The cost: no standalone Schema document to hand a third party. Both ends are on their own to derive the same Schema.

✕

No Optional, no nullable, no explicit default

There is no wire-level marker for absence. No tag, no null byte. A trailing field can end up with no data through Version Skew (§9.1). How an implementation represents that - a default value, Option<T>, an exception - is left to the implementation. Not to the wire format.

✕

No transport, no framing, no crypto

Fomoxa produces a byte sequence and stops. Message boundaries, retransmission, ordering, encryption, compression: build them yourself, on top.

Is any of these unacceptable for your problem? A format with tag IDs and optional fields will serve you better. That is the right call, not a failure of Fomoxa.

RFC-0002

Wire format

Little endian, always. Fixed widths, no varint. No tag, no header, no padding, no terminator. Position is the only identifier.

Primitive

Fixed width, little endian. A u32 is four bytes, even when the value is zero.

u32   100        → [64 00 00 00]
u32   0x12345678 → [78 56 34 12]
i32   -1         → [FF FF FF FF]
u16   300        → [2C 01]
bool  true       → [01]
bool  0x02       → invalid
f32   3.14       → [C3 F5 48 40]
f32   -0.0       → [00 00 00 80]

Floats keep their IEEE 754 bit pattern exactly. No normalization, no canonical NaN.

String

UInt32 length, then UTF-8 bytes. Length counts bytes, never characters.

"abc"      → [03 00 00 00] [61 62 63]
"中"        → [03 00 00 00] [E4 B8 AD]
"Xin chào" → [09 00 00 00] [58 69 6E 20 63 68 C3 A0 6F]
""         → [00 00 00 00]

“中” is one character, three bytes. Length MUST be 3. The byte region MUST be valid UTF-8.

Bytes

UInt32 length, then raw bytes. Identical to String, minus the UTF-8 constraint.

[]         → [00 00 00 00]
[FF FE]    → [02 00 00 00] [FF FE]
[00 00]    → [02 00 00 00] [00 00]

The same bytes a String must reject. Type comes from the Schema, never inferred from content.

Model

Fields concatenated in declaration order. No metadata, no field ID, no padding.

model Item { id: u32; name: String }
Item{ 42, "Sword" }
  → [2A 00 00 00] [05 00 00 00] [53 77 6F 72 64]

model Mixed { a: u8; b: u32; c: u8 }
Mixed{ 1, 2, 3 } → [01 02 00 00 00 03]   6 bytes
                   12 bytes = copying memory layout

A compiler may reorder fields in RAM. That must not change a single byte of output.

Array

UInt32 count, then each element in the byte shape of T. Count is elements, not bytes.

Array<u32> [1,2,3]
  → [03 00 00 00] [01 00 00 00] [02 00 00 00] [03 00 00 00]

Array<String> ["a","bc"]
  → [02 00 00 00] [01 00 00 00 61] [02 00 00 00 62 63]

Array<Array<u8>> [[1,2],[]]
  → [02 00 00 00] [02 00 00 00 01 02] [00 00 00 00]

Count for [1,2,3] is 3, not 12. An empty inner array is a count of 0 and no further bytes.

Enum

Always UInt32. Four bytes, regardless of how few members it declares.

enum PlayerState { Idle=0, Walk=1, Run=2, Jump=3 }

Idle → [00 00 00 00]
Walk → [01 00 00 00]
Jump → [03 00 00 00]
99   → invalid - outside the defined set

A protocol decision, not a storage optimization. There is nothing for two peers to negotiate.

Version skew

The writer and the reader may run two different versions of the same Model. One condition: the only difference is a field appended or removed at the very end. 

model ItemV1 { id: u32 }
model ItemV2 { id: u32; name: String }

written ItemV1, read ItemV2
  [2A 00 00 00] → id=42, bytes end exactly on the boundary before name
                  → valid - name has no data

written ItemV2, read ItemV1
  [2A 00 00 00 05 00 00 00 53 77 6F 72 64] → id=42, 9 bytes remain
                  → valid - the leftover is discarded

written ItemV2, read ItemV2, truncated mid-field
  [2A 00 00 00 05 00 00 00 53 77] → length=5, only 2 bytes of data remain
                  → invalid - Unexpected EOF, NOT version skew

The stopping rule is “does the shortfall or surplus fall exactly on a field boundary?”. Never “is data missing?”. Inserting a field mid-Model, reordering fields, changing a field's type: still a breaking change. See RFC-0002 §9.1.

A complete message, byte by byte

The example from RFC-0002 §15. Nested model, string, integers, bool. It encodes to 31 bytes. Hover a field to light up the bytes it owns. Hover a byte to find its owner. 

model Vector3 { x: f32; y: f32; z: f32 }

model GameMessage {
  playerId:   u32       = 42
  playerName: String    = "Knight"
  position:   Vector3   = { 10.5, 20.3, -5.1 }
  health:     u32       = 100
  isAlive:    bool      = true
}
Hex dump · 31 bytes Position is the only identifier
00000000 2A000000060000004B6E696768740000
00000010 28416666A2413333A3C06400000001
Total31 bytes · 0 bytes of metadata

Nothing separates the fields. No length prefix on the nested model. No delimiter between position and health. No terminator at the end. The decoder knows which field it is reading from how far the cursor has advanced. That is why reordering a field is a breaking change, and why renaming one is free.

Valid only when the shortfall or surplus lands exactly on a field boundary. Compare with N-022 below: bytes go missing mid-field, and it MUST still be rejected. Treating every missing or extra byte as version skew, even mid-field, is the most common conformance bug when adding this support (RFC-0002 §9.1).

Rejection is MUST. The error name is only SHOULD. N-023 and N-031 check one thing: is the length validated before allocating? Crashing and catching the exception does not count as a pass.

The full set is in RFC-0003. It covers 8-byte integers, f64, round-trip checks, and cross-implementation checks.

Conformance

Fomoxa Compatible

An implementation is Fomoxa Compatible if and only if it passes 100% of the test vectors.

  • ✓ RFC-0002
  • ✓ Test Vectors
  • ✓ Deterministic Output

There is no “partially compatible”. There is no 98%. One failing vector means data exists on which two implementations disagree. Silently, in production.

An implementation 10× slower that passes 100% of the vectors is Fomoxa Compatible.
The fastest implementation in the world that fails one vector is not.
